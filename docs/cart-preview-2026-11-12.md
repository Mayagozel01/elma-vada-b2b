## Что установлено об HTTP 403

Пользователь подтвердил на настоящей корзине: одинаковый вариант с **Maya × 1** и **Anna × 2**, итог **$29.97**, персонализация сохраняется. Одновременно при обновлении появлялась страница HTTP ERROR 403 на `/cart`. Это наблюдение пользователя, не независимый тест агента.

В свежем коде до доработки:

- Форма `templates/cart.liquid` использовала `action="{{ routes.cart_url }}" method="post"`.
- **Update cart** — submit с `name="update"`, количества — `updates[]` в порядке строк.
- **Remove** — штатный `item.url_to_remove`.
- **Checkout** — submit с `name="checkout"`.
- `assets/commerce.js` подключался только на странице товара и обрабатывал галерею, варианты, проверку надписи и копирование данных заявки. Он не отправлял корзину через fetch и не вызывал второй submit. Обработчик в `office-visit.js` ограничен формами консультаций.

Эта форма соответствует [документированному шаблону корзины Shopify](https://shopify.dev/docs/storefronts/themes/architecture/templates/cart). По коду причина 403 **не установлена**. Не доказано, возникает ли отказ на POST, на последующем GET после перенаправления или при повторной отправке документа после Refresh. Нет оснований объявлять виновником cookies, домен, защиту Shopify или конкретное приложение.

Чтобы установить причину, нужны данные DevTools → **Network** с включённым **Preserve log** для неудачной операции: URL запроса, HTTP-метод, статус и вся цепочка перенаправлений (URL/метод/статус каждого шага). Полезно указать, нажимался ли Refresh после Update cart. **Cookies, токены, заголовки авторизации и полный HAR не нужны.**

## Перенесённые изменения

1. `assets/cart.js` — новый общий обработчик. Update cart отправляет один POST на локализованный `routes.cart_update_url + '.js'`, только изменённые количества в `updates` с ключами строк `item.key`. Remove отправляет POST на локализованный `routes.cart_change_url + '.js'`, `{id: item.key, quantity: 0}`. Одинаковые variant ID с разными надписями не используются как идентификатор строки. Объект `properties` не отправляется и не перезаписывается. Основа — [Shopify Ajax Cart API](https://shopify.dev/docs/api/ajax/reference/cart).
2. `templates/cart.liquid` — данные ключей/эндпоинтов, сообщение ошибки и обычная ссылка **Reload cart**. Нативные action/method, `updates[]`, `item.url_to_remove` и Checkout сохранены как fallback без JavaScript. При включённом JavaScript повторная отправка заблокирована, пока запрос выполняется. Checkout остаётся штатным POST Shopify, включая несохранённые количества; JavaScript его не воспроизводит через Ajax.
3. `assets/commerce.css` — стиль ошибки и недоступных элементов во время запроса.
4. `sections/header.liquid` — постоянная ссылка **Cart** с иконкой и общим количеством единиц, через `routes.cart_url`. Она расположена вне скрываемых nav/CTA/mobile-menu и видна также при `0`. Логотип, меню и обе CTA сохранены. Здесь же подключается `cart.js` на всех страницах с шапкой.
5. `assets/theme.css` — оформление Cart и размещение в компактной шапке; на узком экране логотип остаётся в верхнем ряду, Cart и меню — в следующем.
6. `assets/theme.js` — ширина Cart учитывается при переключении шапки в компактный режим; изменение счётчика вызывает повторное измерение.

После успешного ответа Ajax выполняется `location.replace(form.action)`: новый **GET** корзины заново выводит серверные цены, скидки, количество, свойства и итог. JavaScript не рассчитывает деньги самостоятельно. Refresh страницы не должен повторять изменяющий POST Update cart. Счётчик обновляется из подтверждённого `item_count`, затем из свежего Liquid при GET. При возвращении к вкладке/восстановлении страницы счётчик обновляется чтением локализованного `/cart.js`; восстановленная из bfcache страница корзины открывается свежим GET.

При HTTP-ошибке, тайм-ауте, сетевом отказе или неожиданном ответе нет автоматического повтора, fallback POST или сообщения об успехе. Появляется **We could not confirm the cart update… Your cart may have changed. Reload the cart before trying again.** Кнопки изменения и Checkout остаются заблокированы до явной перезагрузки через **Reload cart**, потому что потеря ответа не доказывает, что сервер не применил изменение. Ошибка чтения счётчика не заменяет последнее подтверждённое значение нулём.

Это изменение потока обновления и обработки ошибок, **не доказанное устранение причины настоящего 403**. Если отказ возникает на GET `/cart` или штатном Checkout, он может воспроизвестись и требует данных Network.

## Влияние метаполей на активную тему

Свежая активная тема уже содержит реализованное поле и `enable_personalization: true` в Product details. Поэтому заполнение **всех** перечисленных метаполей способно изменить действующий сайт, а не только предпросмотр:

| Метаполе товара | Влияние в свежей активной теме |
| --- | --- |
| `custom.personalization_enabled` | `true` показывает поле, `false`/пусто скрывает. |
| `custom.personalization_required` | `true` делает поле обязательным для вариантов с гравировкой. |
| `custom.personalization_max_length` | Положительное число задаёт лимит; пусто/`0` не задаёт лимита темы. |
| `custom.personalization_no_engraving_values` | Дополняет точные значения опций, отключающих поле для варианта без гравировки. |
| `custom.personalization_note` | Меняет дополнительное пояснение покупателю. |

Условия required/limit/opt-out действуют, когда поле включено. Существующие определения и значения у товаров в Admin не запрашивались и не менялись. Для теста использовать согласованный тестовый товар; сам по себе выбор неопубликованной темы не изолирует изменения метаполей.
